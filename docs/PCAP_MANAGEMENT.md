# Управление сохранёнными PCAP

WireScope хранит сырой PCAP отдельно от нормализованных результатов анализа. Это позволяет как загружать внешний захват для офлайн-анализа, так и удалять крупный или чувствительный raw-файл, не стирая историю уже выполненной работы.

## Ручной импорт PCAP

Оператор с ролью `auditor` может добавить внешний `.pcap` или `.pcapng` через экран **«Прослушивание»** или API:

```text
POST /api/v1/captures/import
Content-Type: application/octet-stream
X-WireScope-Filename: <URL-encoded filename>

<raw PCAP/PCAPNG body>
```

Файл передаётся потоково: API не загружает весь PCAP в память. По умолчанию максимальный размер одного импортируемого файла — **256 МиБ**. Лимит можно изменить переменной окружения:

```text
WIRESCOPE_PCAP_IMPORT_MAX_FILESIZE_MB
```

Допустимый диапазон политики — `1..4096` МиБ.

### Lifecycle

```text
внешний PCAP/PCAPNG
        ↓
bounded streaming upload
        ↓
staging внутри evidence root
        ↓
проверка размера + формата + SHA-256
        ↓
durable packet_capture job
source_origin = imported
        ↓
повторная проверка worker'ом
        ↓
обычный packet_capture artifact
        ↓
Traffic Analysis по явному действию оператора
        ↓
опционально Correlated Assessment
```

Импорт использует тот же downstream lifecycle, что и PCAP, снятый самим WireScope. Поэтому после успешного импорта файл можно:

- скачать;
- удалить обычной кнопкой **«Удалить PCAP»**;
- отправить в существующий Traffic Analysis;
- повторно анализировать, пока raw PCAP сохранён;
- использовать результат Traffic Analysis как явно выбранный источник для Correlated Assessment.

Для PCAPNG сохраняются формат, расширение и корректный media type; файл не маскируется под classic PCAP при скачивании.

### Trust boundary импортированного PCAP

Внешний PCAP считается **историческим недоверенным observation source**. Его содержимое описывает только то, что присутствует в самом файле.

Импортированный PCAP:

- не выполняет network I/O;
- не запускает `dumpcap`, discovery или protocol probes;
- не создаёт и не расширяет подтверждённый active scope;
- не доказывает, что отражённая в файле сеть сейчас подключена к WireScope;
- не разрешает активное сканирование IP/MAC/VLAN, найденных только внутри внешнего файла;
- не смешивается автоматически с текущим аудитом.

Технически это фиксируется как минимум следующими признаками:

```text
source_origin = imported
network_io_performed = false
active_scope_authorized = false
```

Если оператор хочет сопоставить внешний PCAP с результатами конкретного аудита, он сначала запускает обычный Traffic Analysis для импортированного файла, а затем **явно выбирает** этот завершённый Traffic Analysis в Correlated Assessment. Сам факт импорта не создаёт такую связь автоматически.

### Проверка и staging

До создания durable capture job API проверяет:

- файл не пустой;
- размер не превышает configured limit;
- magic/header соответствует поддерживаемому classic PCAP или PCAPNG;
- базовую целостность заголовка;
- SHA-256 всего файла.

После постановки job worker повторно читает staging-файл и сверяет размер/SHA-256 перед регистрацией final `packet_capture` artifact. Это защищает от изменения файла между HTTP upload и durable worker execution.

Staging хранится только под evidence root, использует случайный UUID и права `0600`; временный файл удаляется после обработки или ошибки. Старые `*.tmp-*` также подпадают под существующую очистку временных файлов WireScope.

Успешная операция записывается в operational audit log как:

```text
capture.pcap_import
```

## Ручное удаление

Оператор с ролью `auditor` может удалить сырой файл PCAP через GUI или API:

```text
DELETE /api/v1/captures/{capture_job_id}/pcap
```

Операция удаляет только artifact типа `packet_capture` и его файл на диске.

**Сохраняются:**

- запись сессии захвата/импорта и её статус в durable history;
- immutable `capture_result` / `packet_capture_result` с историческими метаданными;
- уже рассчитанные `traffic_analysis_result`;
- результаты сравнения/корреляции, построенные из ранее сохранённых нормализованных данных;
- operational audit log.

После ручного удаления:

- запись исчезает из обычного списка сохранённых PCAP в GUI;
- скачать исходный PCAP нельзя;
- повторно запустить Traffic Analysis для этого PCAP нельзя;
- уже готовый Traffic Analysis по-прежнему читается и экспортируется;
- историческая capture-job остаётся доступна по её ID и не удаляется из durable history.

Такое разделение намеренное: кнопка «Удалить PCAP» удаляет сохранённый сырой файл и его присутствие в рабочем списке, но не уничтожает уже полученные результаты аудита/анализа.

## Защита от гонок

PCAP нельзя удалить, пока в его capture-audit есть `queued` или `running` job. Сначала нужно остановить или дождаться завершения захвата/анализа.

API возвращает `409 pcap_delete_busy`.

## Retention и отсутствующий файл

`audit.summary` содержит исторические сведения и может пережить автоматическое удаление raw-artifact по retention. Поэтому GUI/API подтверждают наличие PCAP по зарегистрированному artifact и реальному файлу, а не только по старому `pcap_artifact_id` в summary.

Если artifact или файл исчез не через ручное удаление, запись может оставаться в истории захватов с состоянием «PCAP недоступен». Это отличается от явного удаления оператором: вручную удалённая запись скрывается из обычного списка PCAP.

Если artifact или файл уже отсутствует, download endpoint возвращает:

```text
410 pcap_unavailable
```

Повторный `DELETE` безопасен и идемпотентен.

Если metadata уже исключена из WireScope, но физический `unlink()` файла на диске завершился ошибкой, API возвращает `file_cleanup_pending > 0`, а GUI показывает явное предупреждение о необходимости проверить хранилище.

## Безопасность удаления

Перед удалением путь artifact проверяется относительно настроенного evidence root. Метаданные с путём за пределами evidence root не используются для удаления файлов.

Операция фиксируется в operational audit log как:

```text
capture.pcap_delete
```
